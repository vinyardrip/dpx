DPX — это CLI на Bash для управления проектами DDEV. Он добавляет сценарии обновления, снимков, восстановления и выгрузки баз данных; создание проектов WordPress, Joomla, OpenCart, ocStore, Laravel и Plain PHP; туннели Cloudflare и ngrok; смену версии PHP; метаданные проектов; полные бэкапы; миграцию; развёртывание; очистку; диагностику и самообновление.

Слой команд консервативно работает с изменениями данных. Импорты БД, замена URL, смена PHP, патчи конфигурации и настройка туннеля по возможности имеют резервную копию или путь отката.

## Целостность данных

DPX следует политике нулевого доверия при изменении данных:

- Перед разрушительными операциями с БД создаётся локальный снимок, если это предусмотрено сценарием.
- Полное восстановление сайта сначала создаёт страховочный снимок DDEV, а затем распаковывает файлы и импортирует встроенный дамп.
- Для WordPress замена URL выполняется через WP-CLI с `--all-tables`, `--precise` и `--allow-root`.
- Для не-WordPress SQL используется PHP-помощник внутри контейнера `lib/php_helpers/dpx_serialize_safe_replace.php`, который пересчитывает длины сериализованных строк после замены.
- Изменения `wp-config.php` используют скрытый побайтовый снимок, патч, проверку `php -l` через DDEV, проверку маркеров и откат при ошибке.
- Конфигурация Nginx для туннеля записывается как расширение DDEV на хосте и удаляется при очистке туннеля.
- Ctrl+C во время туннеля запускает cleanup-trap: восстанавливает конфигурацию WordPress, отменяет изменения БД, удаляет override Nginx, останавливает провайдер и временное состояние.

### Две подсистемы снимков

DPX использует два независимых механизма восстановления — они хранят данные в разных местах и решают разные задачи:

**1. Файловые SQL-дампы** находятся в центральном каталоге `DPX_DB_LOCAL_DIR` с именами вида `<проект>_<ТИП>_<ггММдд>_<ЧЧММСС>_<рандом>.sql` и тегами типов:

| Тег | Создаётся командой | Хранение |
| --- | --- | --- |
| `SNAP` | `dpx db snap` | 3 последних (фиксировано) |
| `LOCAL_BACKUP` | страховочные дампы `dpx db pull` / `dpx db restore` | 3 последних, настраивается через `local_backup_keep` |
| `TO_PROD` | экспорты `dpx db push` | 3 последних (по умолчанию ротации) |
| `BEFORE_PHP` | `dpx set-php` | 3 последних (по умолчанию ротации) |

Ротация упорядочивает файлы по **метке времени в имени файла** (не по mtime), поэтому дампы, синхронизированные без `--times` или затронутые инструментами восстановления, сохраняют истинный хронологический порядок. Ротация ограничена префиксом `<проект>_<ТИП>_`; файлы других проектов и произвольные файлы, не совпадающие с шаблоном именования DPX, никогда не затрагиваются.

**2. Снимки контейнера DDEV** управляются самим DDEV в `<проект>/.ddev-db-snapshots`. DPX создаёт их (через `ddev snapshot --name=<тег>_<ЧЧММСС>_<рандом>`) перед проходами замены URL в сценариях туннеля, `db pull` и `db push`, и записывает имя снимка в `<проект>/.dpx/current_snapshot`. Если процесс умирает в середине изменения, следующая команда DPX обнаружит оставшийся маркер и предложит автоматически восстановить снимок (восстановление «осиротевшего» состояния). Эти снимки исключаются из полных бэкапов сайта и могут быть освобождены командой `dpx clean --snapshots`.

## Требования

| Зависимость | Минимум | Назначение |
| --- | ---: | --- |
| Bash | 4.0+ | Ассоциативные массивы, nameref, `mapfile` и современные возможности shell |
| DDEV | 1.21.0+ | Жизненный цикл проекта, импорт/экспорт БД, снимки и выполнение в контейнере |
| Docker | 20.10+ | Среда контейнеров DDEV |
| jq | 1.5+ | Разбор JSON DDEV и API ngrok |
| curl, grep, sed, awk, tar | системные | HTTP, обработка текста и архивы |
| PHP CLI | необязательно | Нужен только для отдельных локальных сценариев помощника/тестов; операции WordPress обычно используют PHP внутри DDEV |

### macOS

В macOS установлен Bash 3.2, который не поддерживается. Установите Bash 4.0 или новее через Homebrew и убедитесь, что он находится в `PATH` раньше `/bin/bash`. Реализация определяет macOS и использует совместимый с BSD режим `sed`. Набор тестов также моделирует поведение BSD `sed`, `stat`, `readlink` и tar.

## Установка

```bash
git clone https://github.com/vinyardrip/dpx.git
cd dpx
./install.sh
```

Обычная установка создаёт симлинк в `~/.local/bin`. Для глобальной установки используйте `sudo ./install.sh install-global`, для проверки зависимостей — `./install.sh check`, для удаления — `./install.sh uninstall`. Поддерживаемый способ обновления из Git-репозитория — `dpx update`.

## Быстрый старт

```bash
dpx                         # мастер первого запуска при отсутствии конфигурации
dpx config --show           # показать активные настройки
dpx list                    # список проектов DDEV
dpx new mysite --cms=wordpress --php=8.1 -y
dpx db pull --project-name mysite --db-file mysite_prod
dpx site backup --project-name mysite --output ~/backups --keep 5
dpx tunnel --project-name mysite --provider=cloudflare
```

Мастер первого запуска работает только интерактивно. Неинтерактивные вызовы не зависают, а выводят подсказку с командой `dpx config`. Если найден `cloudflared`, а `ngrok` отсутствует, мастер первого запуска выбирает `cloudflare` по умолчанию.

## Расширенная справка CLI

Все команды поддерживают `-h` или `--help`, если это предусмотрено справкой команды. Глобальные параметры роутера: `-h`, `--help`, `-v`, `--version`, `-y`, `--yes` и `--debug`. Там, где это поддерживает парсер, параметры можно писать как `--key value` или `--key=value`.

### `dpx new`

Создаёт проект DDEV одним из шести scaffold-сценариев. Без `--cms` отображается интерактивный выбор.

| Параметр | Значения / значение по умолчанию | Поведение |
| --- | --- | --- |
| `--project-name NAME` | Также поддерживается позиционное имя | Каталог и имя проекта DDEV |
| `--cms TYPE` | `wordpress`, `joomla`, `opencart`, `ocstore`, `laravel`, `php`; без параметра — интерактивный выбор | Выбирает scaffolder |
| `--type TYPE` | Алиас `--cms` | Алиас для совместимости |
| `--php VERSION` | Значение из конфигурации, обычно `7.4` | Версия PHP DDEV |
| `--db` | По умолчанию выключен | Создаёт данные БД сразу после запуска контейнера |
| `-y`, `--yes` | По умолчанию выключен | Пропускает подтверждения и по возможности делает сценарий неинтерактивным |
| `--archive` | Не является текущим параметром `dpx new` в v1.6.0 | URL архивов разрешаются внутри через environment override, GitHub Releases или исходный архив; поставляемая команда этот параметр не разбирает |
| `--non-interactive` | Не является параметром текущего парсера | Используйте поддерживаемый переключатель `-y` |

Алиасы CMS включают `wp`, `ocs`, `lara`, `html`, `static` и числовые пункты меню `1`–`6`. `dpx new-wp` — совместимый wrapper для `dpx new --cms=wordpress`.

### `dpx site backup`

`dpx site backup` вызывает реализацию legacy-команды `backup` и создаёт `FULL_<project>_<timestamp>.tar.gz`. Архив содержит файлы проекта и дамп БД, если экспорт прошёл успешно. Исключаются тяжёлые и генерируемые каталоги `.ddev/.importdb`, `.ddev-backups`, `backups`, `node_modules`, `vendor` и `.git`.

| Параметр | Значения / значение по умолчанию | Поведение |
| --- | --- | --- |
| `--project-name NAME` | Интерактивный выбор при отсутствии | Проект для бэкапа |
| `--output DIR` | `full_backup_path` | Каталог назначения |
| `--keep N` | `full_backup_keep`, по умолчанию `3` | Количество сохраняемых последних архивов |
| `-y`, `--yes` | По умолчанию выключен | Пропускает подтверждение запуска и бэкапа |

После успешного создания автоматически удаляются старые архивы `FULL_<project>_`, пока не останется заданное количество. Старое написание `dpx backup` продолжает поддерживаться.

### `dpx site restore`

`dpx site restore` восстанавливает архив, созданный полным бэкапом. Если путь к архиву не передан, команда показывает файлы `FULL_*.tar.gz` из `full_backup_path`, начиная с нового.

| Параметр | Значения / значение по умолчанию | Поведение |
| --- | --- | --- |
| `ARCHIVE` | Необязательный позиционный путь | Архив для восстановления |
| `--file FILE` | Необязательный алиас пути | Альтернативный входной архив |
| `--project-name NAME` | Извлекается из `FULL_<project>_<timestamp>.tar.gz`, иначе запрашивается | Целевой проект DDEV |
| `-y`, `--yes` | По умолчанию выключен | Пропускает подтверждение перезаписи |

Порядок восстановления: страховочный снимок, проверка архива, объединяющая распаковка в базу проектов, импорт встроенного дампа, очистка кэша с учётом CMS и запуск DDEV. Снимок перед восстановлением регистрируется в `.dpx/current_snapshot`; trap-обработчики `INT`/`TERM`/`EXIT` пытаются выполнить откат, а при неудаче сохраняют маркер для восстановления осиротевшего состояния. Проверка архива отклоняет `..`/абсолютные элементы, а также цели симлинков и жёстких ссылок за пределами корня распаковки. Архивные файлы перезаписывают совпадающие файлы проекта; дополнительные существующие файлы сохраняются. Старое написание `dpx restore` продолжает поддерживаться.

### `dpx tunnel`

В поставляемой версии v1.6.0 используется `--provider`, а не `--driver`; порт хоста определяется через DDEV. Имена интерфейса `--driver=<cloudflared|ngrok>` и `--port` запланированы, но текущая команда их не разбирает. Используйте поддерживаемую форму ниже.

| Параметр | Значения / значение по умолчанию | Поведение |
| --- | --- | --- |
| `--project-name NAME` | Автоопределение из текущего каталога DDEV, затем интерактивный выбор | Проект для публикации |
| `--cms-type TYPE` | Автоопределение; `wordpress`, `joomla`, `opencart`, `php` | Управляет заменой URL и очисткой CMS |
| `--provider=PROVIDER` | `cloudflare` или `ngrok`; конфигурация, затем доступный провайдер | Выбирает `cloudflared` или ngrok |
| `--driver=<cloudflared\|ngrok>` | Не разбирается в v1.6.0 | Используйте `--provider` |
| `--port PORT` | Не разбирается в v1.6.0; порт определяется DDEV | Используется обнаруженный порт DDEV |
| `-y`, `--yes` | По умолчанию выключен | Пропускает подтверждения |

Для WordPress DPX заменяет URL локальной БД на URL туннеля, добавляет блок `DPX_SMART_TUNNEL` в `wp-config.php` и записывает `.ddev/nginx_full/dpx-tunnel.conf`. Override Nginx отключает `absolute_redirect` и `port_in_redirect`, передаёт публичный `Host` и устанавливает `X-Forwarded-Proto https`, чтобы приложение корректно видело публичный HTTPS-запрос.

Ctrl+C запускает trap отката: восстанавливает `wp-config.php` из снимка, восстанавливает БД из сохранённого снимка DDEV или выполняет резервный обратный search-replace, очищает кэш WordPress, удаляет override Nginx, перезагружает Nginx, останавливает провайдер, удаляет временные файлы и PID-маркеры.

### `dpx db pull`, `dpx db snap`, `dpx db restore`, `dpx db push`

Групповой namespace БД сопоставляется с командами `refresh`, `db-snap`, `db-restore` и `to-prod`. Старые имена остаются действительными.

| Команда | Основные параметры | Значения по умолчанию / поведение |
| --- | --- | --- |
| `dpx db pull` | `--project-name`, `--cms-type`, `--db-file`, `--prod-url`, `--prod-tld`, `--no-backup`, `-y` | Обновляет локальную БД из продакшена; TLD продакшена по умолчанию `by`; защитный бэкап можно отключить `--no-backup` |
| `dpx db snap` | `--project-name`, `-y` | Экспортирует несжатый локальный снимок и сохраняет последние 3 |
| `dpx db restore` | `--project-name`, `--cms-type`, `-y` | Выбирает локальный бэкап, создаёт защитный дамп, импортирует его и запускает post-processing CMS |
| `dpx db push` | `--project-name`, `--cms-type`, `--prod-url`, `--prod-tld`, `-y` | Экспортирует локальную БД с заменой URL на продакшен; TLD по умолчанию `by` |

#### Безопасная замена в базе данных

Отдельной публичной команды `dpx db replace` в роутере v1.6.0 нет. Используемый refresh, deploy, migrate и связанными операциями туннеля путь — функция `db_import_with_replace()` в `lib/database.sh`. Она помещает SQL-дамп и `lib/php_helpers/dpx_serialize_safe_replace.php` в `.dpx/tmp`, запускает PHP-помощник внутри контейнера DDEV, пересчитывает байтовые длины `s:N:` и импортирует изменённый дамп. Это предотвращает повреждение данных Joomla, OpenCart и сериализованных данных WordPress при изменении длины URL.

### `dpx config`

Мастер управляет `~/.config/dpx/dpx.conf`; управляемые ключи обновляются, а посторонние строки сохраняются.

| Параметр | Значения / значение по умолчанию | Поведение |
| --- | --- | --- |
| `--show` | Выключен | Показывает активную объединённую конфигурацию и путь к файлу |
| `--projects-root PATH` | Текущее `ddev_projects_base_path` | Задаёт каталог проектов DDEV |
| `--db-local-dir PATH` | Текущее `DPX_DB_LOCAL_DIR` | Задаёт центральное хранилище локальных снимков и защитных дампов |
| `--db-prod-dir PATH` | Текущее `DPX_DB_PROD_DIR` | Задаёт центральное хранилище дампов продакшена для `db pull` |
| `--backup-dir PATH` | Текущее `DPX_BACKUP_DIR` | Задаёт центральное хранилище полных архивов сайта |
| `--provider NAME` | `ngrok` или `cloudflare` | Задаёт предпочтительный провайдер туннеля |
| `--db-user USER` | `db` | Пользователь БД по умолчанию для scaffold-команд |
| `--db-password PASS` | `db` | Пароль БД по умолчанию |
| `--lang LANG` | `auto`, `en`, `ru`; по умолчанию `auto` | Задаёт язык CLI |
| `-y`, `--yes` | Выключен | Применяет изменения параметров без подтверждения сводки |

Мастер первого запуска спрашивает корень проектов, провайдер, пользователя БД, пароль БД и язык. При отсутствии пользовательского файла он использует `command -v cloudflared` и `command -v ngrok` для выбора провайдера по умолчанию.

Полный порядок мастера: каталог проектов, каталог локальных дампов, каталог дампов продакшена, каталог полных бэкапов, провайдер туннеля, пользователь БД, пароль БД и язык. Первые четыре ответа сохраняются в `~/.config/dpx/config` как канонические переменные `DPX_*`.

### `dpx set-php`

Интерактивно выбирает проект и поддерживаемую DDEV версию PHP. Позиционное имя проекта поддерживается.

| Параметр | Значения / значение по умолчанию | Поведение |
| --- | --- | --- |
| `PROJECT` | Необязательное позиционное имя | Выбирает проект без списка проектов |
| `-y`, `--yes` | Разбирается как глобальный параметр подтверждения | Пропускает поддерживаемые подтверждения |
| `-h`, `--help` | Выключен | Показывает справку команды |

Сценарий получает версии из `ddev debug capabilities`, а при отсутствии результата использует встроенный список, экспортирует бэкап БД с тегом `BEFORE_PHP`, меняет `php_version`, перезапускает DDEV, очищает кэш WordPress при необходимости и предлагает сохранить проверенную версию как метаданные `php_max`. Перед выбором версии выше сохранённого максимума выводится предупреждение.

| Команда | Назначение | Детали реализации |

## Конфигурация

Настройки загружаются каскадом в порядке возрастания приоритета: `/etc/dpx/dpx.conf`, затем локальный `config/dpx.conf` репозитория (поставляемые значения по умолчанию — он никогда не переопределяет явные настройки пользователя), затем `~/.config/dpx/dpx.conf` и `~/.config/dpx/config` для глобальных путей хранения. Последующие файлы переопределяют предыдущие, поэтому пользовательская конфигурация всегда важнее значений из репозитория. Формат — `key = value`. `dpx config` создаёт и поддерживает глобальный файл путей `~/.config/dpx/config` с `DPX_PROJECTS_DIR`, `DPX_DB_LOCAL_DIR`, `DPX_DB_PROD_DIR` и `DPX_BACKUP_DIR`; прикладные и совместимые настройки остаются в `dpx.conf`.

Центральное хранилище находится вне webroot проектов: настроенный каталог проектов содержит проекты DDEV, а `db_local/`, `db_prod/` и `backups/` — локальные дампы, дампы продакшена и полные архивы. Команды БД и сайта используют эти настроенные каталоги, если параметры путей не переданы.

Интерактивные сценарии работы с БД используют двухшаговый выбор. Сначала DPX показывает таблицу проектов со статусом и версией PHP. Затем показывает список файлов дампов от нового к старому, где `[1]` является значением по умолчанию. Имена БД определяются из `.ddev/config.yaml`, конфигурации CMS или `.env`; если безопасное имя определить нельзя, запускается интерактивный запрос имени БД вручную, а в неинтерактивном режиме используется имя проекта.

```ini
DPX_PROJECTS_DIR = ~/projects/php
DPX_DB_LOCAL_DIR = ~/projects/db_local
DPX_DB_PROD_DIR = ~/projects/db_prod
DPX_BACKUP_DIR = ~/projects/backups
```

Совместимые и прикладные настройки остаются доступны в `~/.config/dpx/dpx.conf`:

```ini
ddev_projects_base_path = ~/projects/php
default_tunnel_provider = cloudflare   # ngrok | cloudflare
db_user = db
db_password = db
cli_lang = auto                         # auto | en | ru
default_php_version = 7.4
default_db_type = mysql
default_db_version = 5.7
project_tld = lo
full_backup_path = ~/projects/backups
full_backup_keep = 3
local_backup_keep = 3                   # хранение *_LOCAL_BACKUP_*.sql (db pull / db restore)
auto_update_check = true
```

## Туннели

Cloudflare Tunnel — проверенный и рекомендуемый провайдер. Провайдер ngrok экспериментальный и не тестировался в регионах с ограничениями; геоблокировка upstream может вернуть `ERR_NGROK_9040`. Провайдер задаётся через `default_tunnel_provider` или `--provider=cloudflare|ngrok`.

Драйвер Cloudflare запускает `cloudflared tunnel --url http://127.0.0.1:<host-port>` и передаёт локальный домен через `--http-host-header`. Драйвер ngrok запускает `ngrok http`, читает `127.0.0.1:4040/api/tunnels` и выбирает HTTPS endpoint через jq, Python или fallback на grep.

### Запросы браузера к локальной сети

Когда публичная страница туннеля загружает ресурсы с локального адреса DDEV, Chrome может показать запрос Local Network Access или сломанную вёрстку. Это защита Chrome Private Network Access. Нажмите **Allow**, либо откройте страницу в режиме инкогнито и разрешите запрос там. Публичный URL туннеля не делает локальный origin автоматически доверенным для браузера.

## Безопасный протокол Sudo

`lib/sudo.sh` централизует привилегированные операции. `dpx_sudo` ограничивает аутентификацию значением `DPX_SUDO_MAX_ATTEMPTS` (3) и использует тайм-аут 60 секунд через `timeout`, на macOS — `gtimeout`, а при отсутствии утилит тайм-аута — напрямую `sudo`. После тайм-аута или исчерпания попыток функция завершается с ошибкой и не повторяет запрос бесконечно. Пароль модуль не кэширует; кэш временной метки sudo принадлежит системному `sudo`.

Протокол работы с файлом:

1. Проверить, что исходный файл существует.
2. Создать соседний снимок `.bak` через `cp` и убедиться в успехе операции.
3. Выполнить привилегированную правку через `dpx_sudo`.
4. Проверить результат.
5. Удалить снимок при успехе или восстановить его через `cp`/`dpx_sudo` при ошибке.

Протокол `wp-config.php` использует скрытый файл `.wp-config.php.dpx_bak`. Снимок проверяется на существование, непустое содержимое и побайтовое равенство через `diff -q`. После отката `mv -f` DPX проверяет отсутствие `DPX_SMART_TUNNEL`. При ошибке проверки выводится критическое сообщение для ручной проверки.

## Архитектура и технологический стек

### Структура модулей

```text
dpx.sh                  Точка входа, общая справка и роутер

lib/i18n.sh             Определение локали и движок словаря t()
lib/io.sh               print_* для вывода интерфейса в STDERR
lib/config.sh           Каскадная конфигурация и мастер первого запуска
lib/args.sh             Парсер --key value / --key=value
lib/checks.sh           Проверки DDEV, Docker и осиротевшего состояния
lib/sudo.sh             Безопасный протокол привилегированных файлов
lib/cms.sh              Реестр CMS и обработчики кэша

lib/utils.sh            prompts, валидация и portable file helpers
```

### Движок i18n

`lib/i18n.sh` определяет язык в порядке: явный `DPX_LANG`, настроенный `cli_lang` со значением `en` или `ru`, `LC_ALL`, `LANG`, затем английский. Функция `t KEY [printf-args...]` выбирает русский словарь при языке `ru`, иначе канонический английский словарь, и форматирует placeholders через `printf -v`. Пользовательский текст команд должен проходить через `t`; технические идентификаторы `DDEV`, `wp-config.php`, имена провайдеров и синтаксис команд не переводятся.

### Кроссплатформенный слой

`lib/paths.sh` определяет Linux или macOS и сохраняет режим встроенного `sed`. Код по возможности не зависит от GNU-специфики: BSD/GNU `sed` используют расширение снимка текущей платформы, разрешение симлинков выполняется обычным `readlink`, метаданные файлов получают переносимым `du`/`awk`, а порядок параметров архиватора совместим с GNU tar и bsdtar. Набор симуляции macOS предоставляет shims, которые отвергают несовместимые GNU-флаги и позволяют обнаруживать регрессии до запуска на настоящем macOS.

### Правила взаимодействия человека и AI

Репозиторий разделяет вывод команд, данные и состояние тестовых процессов:

- Функции, возвращающие данные, пишут результат в stdout; интерфейс пишется в stderr.
- Перед динамической загрузкой роутер проверяет файлы команд через `bash -n`.
- Тесты используют изолированные временные каталоги и mock DDEV, Docker, Git, сети и бинарных файлов провайдеров.
- Подпроцессы, которые должны завершиться или не должны читать интерактивный ввод, используют явное перенаправление stdin `</dev/null`; это не даёт унаследованным pipe или терминалу повесить дочерний процесс.
- Фоновые процессы провайдера и update-check очищаются teardown тестов.
- Тесты должны проверять как успешные, так и ошибочные пути, включая откат и очистку.

## Тестирование и контроль качества

Полный набор запускается так:

```bash
./run_tests.sh
```

Runner сначала выполняет ShellCheck gate, затем запускает наборы core, config, domain routing, cleanup, universal project creation, i18n, tunnel patches/provider parsing, macOS/BSD simulation и hardening-регрессии. Gate покрывает `dpx.sh`, `install.sh`, `run_tests.sh`, все модули `lib/` и `commands/`, а также наборы тестов; файлы анализируются по отдельности, чтобы проверка оставалась быстрой. Полезные отдельные команды:

```bash
bash tests/test_hardening.sh
bash tests/test_i18n.sh
bash tests/test_config.sh

```

В репозитории v1.9.2 есть покрытие Linux и симуляция Darwin. Реальный macOS, WSL2 и полевое тестирование остаются отдельными пунктами roadmap.

## Решение проблем

### Сломанная вёрстка Cloudflare или ngrok

Если ресурсы запрашиваются с `.ddev.site` или другого локального адреса, Chrome может заблокировать их из-за Private Network Access. Нажмите **Allow** в запросе Local Network Access или повторите в режиме инкогнито. В developer tools браузера проверьте, что заблокированные запросы действительно направлены к локальному origin, а не к публичному туннелю.

### `ERR_NGROK_9040` в ngrok

Это означает географическое ограничение или политику доступа на стороне ngrok. Проверьте аккаунт и authtoken, а в регионах с ограничениями предпочитайте `--provider=cloudflare`.

### Прерванный туннель

Запустите новую команду DPX из проекта или проверьте `.dpx/current_snapshot`, `.dpx/tunnel.pid` и скрытое состояние бэкапа WordPress. При следующей подходящей команде DPX выполняет восстановление осиротевшего состояния; если автоматическое восстановление не завершилось, используйте записанное имя снимка DDEV и не удаляйте его до проверки состояния БД.
